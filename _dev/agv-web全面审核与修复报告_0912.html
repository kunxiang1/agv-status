AGV 实时监控 · 全面代码审核与修复

对象：agv-web（海康 RCS-2000 私有推送 Web 监控） · 范围：全项目（config.py / rcs_push.py / server.py / index.html / parse_map.py / _dev） + 对外服务（ZMTP 代理）运维面 · 验证：现场真实产线数据端到端 + 5 组离线回归 · 备份：*.bak-0912

01设计意图与整体架构（审核前提）

项目是纯标准库 + 原生 HTML/JS 的零依赖监控页，链路是一条"单向管道"：

数据源
海康 RCS-2000 私有 ZMTP 推送通道（6990 状态/路径、8790 告警）， 每车约 208ms 一帧 ≈ 5Hz；官方 REST（8083）已弃用——精度不够是动画"不跟手"的根因
后端 server.py
仅两条订阅连接（数据 + 告警）→ 解析成事件 → 广播； 浏览器侧用 SSE 共享同一条订阅；断线自愈（重登录重连 / EventSource 重连）
前端 index.html
事件 → ingest（帧可信度分层：重复帧停等、步速>2.5m/s 弃坐标） → stepAgv（导航式弧长推进：车是折线上的弧长 s，s 只增不减，上报坐标只作证据不作自由坐标） → canvas 渲染
设计底线
线绝不斜穿空白（斜段沿路网 BFS 绕）；结构上不可能往回走； 动画允许落后真实车 0～1 个上报周期，但永不越过证据点

理解这一点是判定下面所有问题的基准：动画的一切位移都必须有"路上的证据"支撑， 而"页面曾经不渲染"这段时间恰恰没有渲染证据——这正是缺陷二的发生地。

03要求二：切回前台「AGV 飞」的根因与修复

3.1 复现与量化

用真实抽取的引擎函数 + 虚拟时钟做确定性仿真（_dev/_resume_test.js）：车以 1m/s 沿路走， 上报 208ms 一次；前台正常跑 10s 后模拟"后台挂起"（不出帧，但数据通道照常投递），40s 后恢复。

场景积压弧长修复前修复后
挂起 40s40.3 m 恢复后首帧仍停在 40m 前；随后 3s 内沿轨迹自行补帧 5.80m（≈2m/s 全速冲刺，按此速率要飞 20 秒） 恢复首帧即落在最新上报位置（误差 0），随后 3s 自行补帧 0.00m
挂起 1.2s1.4 m 恢复后 3s 内自行补帧 1.07m（短促一窜） 0.00m
根因链
后台标签的 requestAnimationFrame 被浏览器挂起/节流，但 SSE 仍投递、ingest 仍在把 sEnd 推向最新上报位置；而 s（动画已走到的弧长）不动 → 两者之间积压出几十米。 回前台后 frame 照常推进，迟到追帧分支 (sEnd-s)/max(tl,0.1) 一见"迟到" 就取全部积压除以 0.1s，被 2m/s 上限截断后仍是一段持续数十秒的全速冲刺—— 这就是"残留的未渲染数据被快速连续渲染"造成的瞬间位移。
同时 ingest 会把挂起时长（几万毫秒）当成本次推送周期喂给节奏 EMA，使 vCyc 分母暴涨， 表现为"先僵住、再一窜"。

3.2 修复

位置措施
stepAgv / resyncAgv 重构 把逐车推进从 frame 里抽出成与渲染、DOM 解耦的纯函数。 frame 拿到钳制前的原始帧间隔：若 > RESUME_GAP_S(0.5s)（或积压 > RESYNC_DIST(8m)） 即判定"页面曾挂起"，本帧对每车只调 resyncAgv：位置落到最新上报点、 清空 s/sEnd 积压、按最新 path 重锚折线。一次就地收敛，不补跑走过的路。
ingest 上报间隔 > SUSPEND_GAP_MS(1.5s) 视为推送长断：该间隔不进 _gap EMA， 按标称节奏计 vCyc，避免恢复瞬间拿错误预算冲刺
frame 调度 resumed || 积压>RESYNC_DIST ? resyncAgv(a) : stepAgv(a,dt)； dt 仍钳在 0.25s 内作为双保险

关于"代价"的说明：挂起期间车确实在真实行驶，恢复时它必然出现在新位置—— 这是唯一诚实的画法（等价于导航 App 切回来的车标重定位）。修复消除的是被渲染成一段持续数秒的追赶动画， 而不是"车标出现在正确位置"这件事本身。

稳态零回归
修复不碰正常路径上的任何公式：仿真里 6s 稳态位移与滞后在修复前后逐位相同（5.64m / 0.19m）， 60s 长跑滞后 0.35m → 0.27m（有界恒定偏移，不发散），车头速度不超过真实车速。 修复前那份旧逻辑仍以"对照组"形式留在测试文件里，保证断言有效。

07架构确认：本机是否已经是「ZMTP 代理」

结论：当前架构已经就是你要的形态——本机是唯一与 RCS 通讯的节点，其它主机只访问本机的 8899。 这不是"应该改成这样"，而是现有代码的实际行为，已逐条取证：

你的要求现状证据
只有本机和 ZMTP 通讯✔ 已满足 全项目只有 rcs_push.py 建 socket；server.py 启动时按 config.push_targets() 起 2 条订阅线程（6990 数据 + 8790 告警），除此之外没有任何地方连 RCS
其它主机访问本机 8899✔ 已满足 服务端本就绑 0.0.0.0（非 127.0.0.1），任意主机可访问
不需要客户端直接向 ZMTP 请求数据✔ 已满足 在 index.html / status.js / alarm.js 里检索 rcs-ip.* / 6990 / 8790 / 8181 / 8083 / socket： 只命中一句注释；四次后端调用（api/config、maps/*.json、/api/events、 /api/syncMaps）全部是相对路径，因此换任何主机打开都自动指向那台服务器
本机拿数据后渲染✔ 已满足 数据经 本机解析 → SSE 广播 → 各浏览器各自渲染；RCS 侧永远只看到一个订阅者， 人多也不会给 RCS 加负载（多标签共享同一条订阅）
一个容易被忽略的好处
RCS 的推送准入是按「发起 Web 登录的那台机器 IP」记录的。既然只有本机登录， 那就只有本机需要能连 RCS、只有本机需要在 RCS 侧"有位置"；其它主机哪怕是普通办公机、 装不了 RCS 客户端、不在任何白名单里，只要能访问本机 8899 就能看监控。

7.1 本轮为「对外提供服务」补齐的运维面

架构本身不用改，缺的是把它当服务交付出去时该有的东西，全部落在 config.py + server.py：

新增说明
启动横幅 直接打印可分发给他人的 URL：自动探测非 127 网卡（优先选通往 RCS 的那块）， 并给出监听地址、访问控制状态、同步节流值。实测输出： 其它主机 http://本机ip:8898/?map=BB
ACCESS_KEY 可选访问密钥（默认空＝开放，内网零门槛）。首次 ?k=密钥 打开后服务端下发 cookie（一年）， 之后刷新/收藏都不用再带；/api/* 与 SSE 一并受控。未带密钥时返回一页中文提示而不是空白
ALLOW_IPS 可选来源限制，写法即语义：写完整地址＝精确、以点结尾＝匹配整段（如 "client-ip."）、 不完整且无结尾点＝宽容前缀

7.2 过程中发现并修掉的两个「我自己引入」的缺陷

这两个值得记下来，都是自查时靠"接口真的通不通"抓到的
  1. 门禁函数语义反转：_gate() 约定"返回 True＝已拦截"，但放行分支也写了 return True， 结果是：请求既不报错、也不返回任何内容——连接建立后被静默关闭。 典型症状是 curl 报 Empty reply from server 而服务端一条日志都没有； 若不是逐个端点实测，这种"静默吞掉全部请求"极易被误判成网络问题。
  2. 降噪函数挂错了类：上一轮为屏蔽断连堆栈加的 handle_error 写在了 handler 上， 而 socketserver 调用的是 server 实例的 handle_error—— 那段代码是死代码，等于白加。已改为继承 ThreadingHTTPServer 覆写。
  3. 另外把 IP 白名单的 startswith 误放行修掉了：原先「精确」写法实际按前缀匹配， 会连带放行同前缀的邻居地址（如以 8 结尾的写法顺带放行了 80 结尾），现已按写法区分精确/前缀。
